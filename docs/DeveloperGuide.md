## 1. Project Overview

ChainLancer is a **decentralised freelancing platform** built on Ethereum (EVM-compatible chains). The platform uses smart contracts to manage escrow, milestone-based payments, reputation, and dispute resolution for freelance jobs.

### Core Workflow

1. **Client** posts a job with milestones and locks USDC funds in the escrow contract.
2. **Freelancer** applies, gets selected, stakes a behaviour deposit, and the job becomes active.
3. Freelancer submits deliverables per milestone; client reviews and approves (or auto-approve triggers after a timeout).
4. If a dispute arises, either party raises one; a **Judge** (assigned by an **Admin**) reviews encrypted evidence and issues a ruling.
5. Funds are redistributed per the ruling, and reputation scores are updated on-chain.

### Actors

| Role | Description |
|------|-------------|
| **Client** | Posts jobs, selects freelancers, reviews milestones, raises disputes |
| **Freelancer** | Applies to jobs, stakes deposit, submits deliverables, raises disputes |
| **Judge** | Reviews dispute evidence, submits rulings (assigned by admin) |
| **Admin** | Manages platform roles (grant/revoke), assigns judges to disputes |

## 4. Getting Started

### Prerequisites

- Node.js ≥ 18
- npm (comes with Node.js)
- MetaMask browser extension
- A Pinata account with JWT token and dedicated gateway

### Smart Contract Setup

```bash
# From the repository root
npm install
npx hardhat compile          # Generates artifacts/ and typechain-types/
npx hardhat node             # Starts a local Hardhat node on http://127.0.0.1:8545
# In a separate terminal:
npx hardhat run scripts/deploy.ts --network localhost
```

The deploy script prints the deployed contract addresses. Copy them into `frontend/.env`.

### Frontend Setup

```bash
cd frontend
npm install
cp .env.example .env         # Then fill in contract addresses and Pinata credentials
npm run dev                  # Starts Vite dev server at http://localhost:5173
```

### MetaMask Configuration (Local)

1. Add a custom network: RPC URL `http://127.0.0.1:8545`, Chain ID `31337`, Currency `ETH`.
2. Import Hardhat's pre-funded accounts using the private keys printed when `npx hardhat node` starts.
3. Typical assignment: Account 0 = Admin/Deployer, Account 1 = Client, Account 2 = Freelancer, Account 3 = Judge.

### Available Scripts

| Script | Command | Description |
|--------|---------|-------------|
| Dev server | `npm run dev` | Start Vite dev server (port 5173) |
| Build | `npm run build` | Production build to `dist/` |
| Preview | `npm run preview` | Serve production build locally |
| Lint | `npm run lint` | ESLint check |
| Test | `npm test` | Run Vitest test suite |
| Test (watch) | `npm run test:watch` | Run Vitest in watch mode |

## 5. Frontend Architecture

### Provider Hierarchy

```
<BrowserRouter>
  └── <WalletProvider>           # Wallet connection state
        └── <ContractProvider>   # Contract instances (read + write)
              └── <Layout>       # Navbar + Footer + <Outlet />
                    └── <Routes>  # Page components
```

All page components render inside `<Layout>`, which provides the navigation bar and footer. `WalletProvider` must wrap `ContractProvider` because contract instances depend on the wallet's signer.

### Routing Table (Current)

| Path | Page Component | Description |
|------|---------------|-------------|
| `/` | `Dashboard` | Overview: stats, active jobs, faucet |
| `/browse` | `BrowseJobs` | Search & filter open jobs |
| `/post-job` | `PostJob` | Client creates a new job |
| `/job/:id` | `JobDetail` | Full job view with milestones & actions |
| `/apply/:id` | `ApplyJob` | Freelancer submits an application |
| `/dispute/:jobId/:milestoneIdx` | `DisputeDetail` | Dispute evidence & status |
| `/profile` | `Profile` | Own reputation profile |
| `/profile/:address` | `Profile` | View another user's profile |
| `/wallet` | `Wallet` | USDC balance, withdrawals, key mgmt |

### Data Flow Pattern

```
User Action
  → Hook function (e.g., useJobEscrow.postJob())
    → Contract call via ethers.js (write contract with signer)
      → Transaction submitted → wait for confirmation
        → Toast notification (loading → success/error)
          → UI state refresh
```

All write operations go through ethers.js `Contract` instances created in `ContractContext`. Read operations use a fallback `JsonRpcProvider` so data loads even without a connected wallet.

## 7. Context Providers

### `WalletContext` (`src/contexts/WalletContext.tsx`)

Manages wallet connection state via `useReducer`.

**State Shape**:

```typescript
interface WalletState {
  account: string | null;        // Connected address (checksummed)
  chainId: number | null;        // Current chain ID
  provider: BrowserProvider | null;
  signer: JsonRpcSigner | null;
  isConnecting: boolean;
  error: string | null;
}
```

**Exposed Functions** (via `useWallet()` hook):

| Function | Description |
|----------|-------------|
| `connect()` | Requests MetaMask account access, sets up provider/signer |
| `disconnect()` | Clears wallet state (does not revoke MetaMask permission) |
| `switchNetwork(chainId)` | Prompts MetaMask to switch or add the target network |
| `isConnected` | Derived boolean — `account !== null` |

**Behaviour**:
- Listens for MetaMask `accountsChanged` and `chainChanged` events.
- Auto-reconnects if a previously connected account is detected on mount.
- Validates the current chain against supported networks.

### `ContractContext` (`src/contexts/ContractContext.tsx`)

Creates and caches ethers.js `Contract` instances.

**Exposed via `useContracts()`**:

```typescript
interface ContractContextType {
  contracts: {
    jobEscrow: Contract | null;
    dispute: Contract | null;
    reputation: Contract | null;
    dataAvailability: Contract | null;
    mockUSDC: Contract | null;
  } | null;
  readContracts: {
    jobEscrow: Contract | null;
    dispute: Contract | null;
    reputation: Contract | null;
    dataAvailability: Contract | null;
    mockUSDC: Contract | null;
  } | null;
}
```

- **`contracts`** — Write-capable instances (require a connected signer). `null` when wallet is not connected.
- **`readContracts`** — Read-only instances using a fallback `JsonRpcProvider`. Always available, even without a connected wallet. Created using the network's RPC URL from `networks.ts`.

Both sets of contracts are recreated when the wallet's `signer` or `chainId` changes.

## 8. Hooks

### `useJobEscrow` (`src/hooks/useJobEscrow.ts`)

The primary hook for all JobEscrow contract write operations. Uses the `contracts` object from `ContractContext`.

**Internal Helper — `execute()`**:
All write operations follow the same pattern via an internal `execute()` function:
1. Validate wallet & contract are available.
2. Call the contract method → receive `TransactionResponse`.
3. Show `toast.loading("Waiting for confirmation...")`.
4. `await tx.wait()` for on-chain confirmation.
5. Show `toast.success(...)` or `toast.error(parseContractError(e))`.

**Functions Provided**:

| Function | Solidity Method | Description |
|----------|----------------|-------------|
| `postJob(params)` | `postJob(...)` | Post a new job with milestones. Params: `title`, `description`, `requirements`, `milestoneAmounts[]`, `reviewTimeout`, `agreementCID`, `agreementHash` |
| `applyForJob(jobId, proposalCID)` | `applyForJob(jobId, proposalCID)` | Submit an application with IPFS proposal |
| `selectFreelancer(jobId, freelancer)` | `selectFreelancer(jobId, freelancer)` | Client selects a freelancer |
| `confirmAndStake(jobId)` | `confirmAndStake(jobId)` | Freelancer stakes deposit to activate job |
| `submitMilestone(jobId, idx, deliverableCID)` | `submitMilestone(jobId, idx, cid)` | Submit deliverable for a milestone |
| `approveMilestone(jobId, idx)` | `approveMilestone(jobId, idx)` | Client approves a milestone |
| `triggerAutoApprove(jobId, idx)` | `triggerAutoApprove(jobId, idx)` | Anyone triggers auto-approve after timeout |
| `raiseDispute(jobId, idx)` | Calls `Dispute.createDispute(jobId, idx)` | Raise a dispute on a milestone |
| `submitEvidence(disputeId, evidenceCID)` | Calls `Dispute.submitEvidence(disputeId, cid)` | Submit encrypted evidence to a dispute |
| `withdraw()` | `withdraw()` | Withdraw accumulated USDC balance |
| `cancelJob(jobId)` | `cancelJob(jobId)` | Cancel a job (pre-active) or request cancellation (active) |
| `acceptCancellation(jobId)` | `acceptCancellation(jobId)` | Freelancer accepts cancellation request |

### `useJobList` (`src/hooks/useJobList.ts`)

Fetches job data from the chain using `readContracts`.

**Functions Provided**:

| Function | Returns | Description |
|----------|---------|-------------|
| `fetchJobs()` | `Job[]` | Iterates `nextJobId` and calls `getJobInfo()` for each. Filters out non-existent (zero-address) entries. |
| `fetchSingleJob(id)` | `{ job, milestones, applications }` | Fetches full job details including all milestones (via `getMilestoneInfo()`) and applications (via `getApplicationCount()` + `getApplication()`). For disputed milestones, also fetches dispute phases via `disputeIds()` + `getDisputeStatus()`. |

**Type Definitions**:

```typescript
interface Job {
  id: number;
  client: string;
  freelancer: string;
  totalAmount: bigint;
  state: number;           // JobState enum
  title: string;
  description: string;
  requirements: string;
  reviewTimeout: number;
  milestoneCount: number;
  createdAt: number;       // Unix timestamp
}

interface Milestone {
  amount: bigint;
  status: number;          // MilestoneStatus enum
  deliverableCID: string;
  submittedAt: number;
  reviewDeadline: number;
  disputePhase?: number;   // Fetched for disputed milestones
}

interface Application {
  applicant: string;
  proposalCID: string;
  timestamp: number;
}
```

## 9. Pages

### `Dashboard` (`src/pages/Dashboard.tsx`)

The landing page after wallet connection. Displays:

- **Stats Grid**: Total jobs, open jobs, active jobs, completed jobs (fetched from job list).
- **Client Section** (if user is a client): Active jobs posted, open listings.
- **Freelancer Section** (if user is a freelancer): Jobs the user is assigned to.
- **Faucet Panel**: Testnet USDC minting widget.

### `BrowseJobs` (`src/pages/BrowseJobs.tsx`)

Job discovery page with:

- **Search bar**: Filters by title/description (client-side).
- **State filter buttons**: All / Open / Active / Completed.
- **Job cards grid**: Renders `<JobCard>` for each matching job.

### `PostJob` (`src/pages/PostJob.tsx`)

Multi-step form for job creation:

1. **Basic Info**: Title, description, requirements (text inputs).
2. **Milestones**: Dynamic list — add/remove milestones with amounts (USDC). Validates each ≥ 10% of total.
3. **Review Timeout**: Dropdown selector (1–30 days).
4. **Agreement**: Text area for agreement content. Encrypted (AES-256-GCM) and uploaded to IPFS.
5. **Cost Summary**: Shows total amount, protocol fee, behaviour bond, freelancer deposit.
6. **Submit Flow**: Approve USDC → Post Job (two MetaMask transactions).

The flow generates a job key, encrypts the agreement, uploads to Pinata, computes an on-chain agreement hash, and calls `postJob()`.

### `JobDetail` (`src/pages/JobDetail.tsx`)

The most complex page. Displays complete job information and all available actions:

- **Header**: Title, state badge, dates.
- **Parties**: Client & freelancer addresses (linked to profile).
- **Financials**: Total amount, protocol fee, behaviour bond, deposit, per-milestone breakdown.
- **Agreement Modal**: Fetches encrypted agreement from IPFS via DataAvailability CID, decrypts with stored job key.
- **Dispute Banners**: For disputed milestones, shows dispute status and phase.
- **Applications List**: Shown when job is Open; client can select a freelancer.
- **Milestone Timeline**: Visual timeline with status badges and countdown timers.
- **Milestone Actions**: Context-sensitive action buttons (Submit / Approve / Auto-Approve / Raise Dispute).
- **Job Actions**: Cancel, Accept Cancellation, Confirm & Stake, Withdraw.

### `ApplyJob` (`src/pages/ApplyJob.tsx`)

Application form for freelancers:

- Loads job details to display context.
- Proposal text area → encrypted and uploaded to IPFS.
- Checks "already applied" status and blocks duplicate applications.
- Calls `applyForJob(jobId, proposalCID)`.

### `DisputeDetail` (`src/pages/DisputeDetail.tsx`)

Displays dispute information and allows evidence submission:

- **Dispute Info**: Phase, ruling, parties, milestone reference.
- **Evidence List**: Fetches evidence from the Dispute contract (`getEvidenceCount` / `getEvidence`), retrieves content from IPFS.
- **Submit Evidence**: File upload + text description, encrypted and uploaded to IPFS, then `submitEvidence(disputeId, cid)`.
- **Key Distribution**: Placeholder for distributing the job decryption key to the assigned judge.

### `Profile` (`src/pages/Profile.tsx`)

Dual-section reputation display:

- **Freelancer Profile**: Score, tier badge, jobs completed, total value earned, success rate.
- **Client Profile**: Score, jobs posted, total value, dispute rate.
- **Job History**: Lists jobs associated with the address (as client or freelancer).
- Tier is computed from on-chain `getFreelancerTier()`.

### `Wallet` (`src/pages/Wallet.tsx`)

Financial management page:

- **USDC Balance**: Current wallet balance.
- **Withdrawable Balance**: Funds available to withdraw from the escrow contract.
- **Withdraw Button**: Calls `withdraw()` on JobEscrow.
- **Faucet**: Mint + approve test USDC.
- **Stored Job Keys**: Lists all locally-stored job keys (from `localStorage`), allows deletion.

## 11. Crypto Module

Location: `src/crypto/`

This module handles all client-side encryption. **All encryption happens in the browser — nothing is sent to a backend.**

### `aes.ts` — AES-256-GCM Encryption

Uses the browser-native **Web Crypto API**.

| Function | Signature | Description |
|----------|-----------|-------------|
| `encryptText(key, plaintext)` | `(CryptoKey, string) → Uint8Array` | Encrypts UTF-8 text. Output format: `[IV (12 bytes) ‖ ciphertext]` |
| `decryptText(key, data)` | `(CryptoKey, Uint8Array) → string` | Decrypts the above format back to string |
| `encryptFile(key, file)` | `(CryptoKey, File) → Uint8Array` | Encrypts file contents (same binary format) |
| `decryptFile(key, data)` | `(CryptoKey, Uint8Array) → ArrayBuffer` | Decrypts file binary |

The IV (initialisation vector) is 12 random bytes prepended to the ciphertext. A new IV is generated for each encryption operation.

### `hash.ts` — Hashing

| Function | Signature | Description |
|----------|-----------|-------------|
| `computeAgreementHash(salt, plaintext)` | `(string, string) → string` | `keccak256(abi.encodePacked(salt, plaintext))` — stored on-chain for tamper detection |
| `computeContentHash(data)` | `(Uint8Array) → string` | `keccak256` of raw bytes |

### `jobKey.ts` — Key Generation

| Function | Signature | Description |
|----------|-----------|-------------|
| `generateJobKey()` | `() → CryptoKey` | Generates a random AES-256-GCM key via Web Crypto |
| `generateSalt()` | `() → string` | Random 32-byte hex string for agreement hashing |
| `importJobKey(rawBytes)` | `(Uint8Array) → CryptoKey` | Imports raw key material into a `CryptoKey` object |
| `exportJobKey(key)` | `(CryptoKey) → Uint8Array` | Exports `CryptoKey` to raw bytes |
| `keyToHex(key)` / `hexToKey(hex)` | — | Conversion between hex strings and `CryptoKey` |

Job keys are stored in `localStorage` using the pattern `chainlancer_jobkey_{jobId}`.

### `keyExchange.ts` — Key Exchange

> ⚠️ **Current implementation differs from the Stage 2 plan.** See [§16 Gap Analysis](#16-gap-analysis--what-remains-to-be-done) for details.

The current implementation uses **MetaMask `personal_sign`** to derive an ECDH shared secret:

| Function | Signature | Description |
|----------|-----------|-------------|
| `encryptForRecipient(jobKey, recipientAddress, signer)` | `(Uint8Array, string, Signer) → Uint8Array` | Derives shared secret via `personal_sign`, uses HKDF to produce an AES wrapping key, then AES-GCM-wraps the job key |
| `decryptWithPrivateKey(encryptedPackage, senderAddress, signer)` | `(Uint8Array, string, Signer) → Uint8Array` | Reverses the above process to recover the job key |

This approach works but has limitations:
- Requires both parties to be online and sign a message.
- Does not use threshold encryption (a single MetaMask signature grants full decryption capability).

| **Mobile** | Desktop-first, basic responsive | Full mobile-responsive design |

| **Lit Protocol** | Not yet integrated (MetaMask-based key exchange) | Threshold encryption via Lit SDK (Datil-dev test network for demo) |
